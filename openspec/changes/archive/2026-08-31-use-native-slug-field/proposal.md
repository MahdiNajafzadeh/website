## Why

Four Payload collections (`Brands`, `Categories`, `Products`, `Posts`) currently auto-generate their `slug` field with an identical hand-rolled pattern: a 6-line `slugify` function plus a `beforeValidate` hook, duplicated verbatim across all four files. The pattern works silently on save but provides no UI affordance (no "generate" button, no lock/unlock), no real uniqueness check at the validation layer, and no `<singular>-N` fallback when the source field is empty. Payload CMS 3.88 ships a native `type: 'slug'` field (`slugField()` from `payload`) that provides all of this — visible generate button, lock/unlock UX, server-side uniqueness dedupe, `<singular>-N` fallback — and the official ecommerce template uses it for `Products`, `Categories`, and `Posts` in a single 4-line declaration per collection. We should adopt it for consistency with Payload's intended workflow and to delete ~60 lines of duplicated logic.

## What Changes

- **Replace** the `type: 'text'` `slug` field definition in `src/collections/Brands.ts`, `src/collections/Categories.ts`, `src/collections/Products.ts`, and `src/collections/Posts.ts` with the native slug field by calling `slugField({ useAsSlug: 'name', position: undefined })` from `payload` (`payload/dist/fields/baseFields/slug/index.js`, exported as `slugField`). On `payload@4.0.0-canary` and later, the equivalent literal `{ name: 'slug', type: 'slug', useAsSlug: 'name' }` is also accepted; on `payload@3.88.0` (our installed version) the `slugField()` factory is the only version-portable form since `'slug'` is not yet in the `FieldType` union.
- **Delete** the duplicated `slugify` function and the `hooks.beforeValidate` entry from all four collection files. The native field provides equivalent generation with correct semantics.
- **Adopt** the native field's UI: the slug input is locked by default with a lock/unlock button next to it; an unlock exposes a "generate" button that re-runs the slugify function server-side via `slugifyHandler` (in `@payloadcms/next/dist/utilities/slugify.js`).
- **Behavior change (BREAKING):** `slug` becomes `required: true` on all four collections (matching the native field default). For `Posts` this is unchanged. For `Brands`, `Categories`, `Products` this was previously `required: false`. The native field's `<singular>-N` fallback (e.g. `products-1`) ensures save succeeds even when `name` is empty on create — the document is saved with an auto-generated fallback slug rather than failing validation. Editing an existing document whose `slug` is already set preserves it; once set, the slug never regenerates automatically (admin must click "generate" or unlock + edit).
- **No changes** to any other field, hook, access rule, or collection-level setting. The `Posts.beforeChange` hook that sets `publishedAt` is untouched.

## Capabilities

### New Capabilities

_None._ The slug-field behavior is local to existing collection requirements; no new capability is introduced.

### Modified Capabilities

- `collection-brand`: Add a "Brand Slug" requirement describing native `type: 'slug'` field behavior — unique, required, derived from `name` (via `useAsSlug: 'name'`), editable via admin lock/unlock, regenerable via the "generate" button, with `<singular>-N` fallback on create when `name` is empty.
- `collection-category`: Add a "Category Slug" requirement with the same native-field behavior, derived from `name`.
- `collection-product`: Add a "Product Slug" requirement with the same native-field behavior, derived from `name`.
- `collection-post`: Modify the existing "Post Slug" requirement (`specs/collection-post/spec.md:28`) to reflect the native-field semantics — generated by the system (not optional), editable via lock/unlock, regenerable via the "generate" button, and the `<singular>-N` fallback on create when `name` is empty. The existing uniqueness requirement and `/blog/[slug]` accessibility requirement are preserved.

## Impact

- **Code (modified):**
  - `src/collections/Brands.ts` — replace slug field config, delete `slugify` fn + `hooks.beforeValidate`.
  - `src/collections/Categories.ts` — same shape as Brands.
  - `src/collections/Products.ts` — same shape as Brands.
  - `src/collections/Posts.ts` — same shape; `beforeChange` (publishedAt) and `afterChange` (ISR revalidation) hooks preserved.
- **Generated artifacts (regenerate):**
  - `src/payload-types.ts` — `bun run generate:types` (slug field type narrows).
  - `src/app/(payload)/admin/importMap.js` — `bun run generate:importmap` (SlugField is already registered via `@payloadcms/next/client`; should be a no-op or add one entry).
- **API:** `POST /api/{brands,categories,products,posts}` body schema is unchanged (slug is still a top-level string); behavior on empty slug shifts from "saved as empty/null" to "filled with `<singular>-N` fallback by server".
- **Database:** SQLite (`payload.db` / `website.db`). Slug columns already exist as `unique` indexes; the native field's uniqueness validation is application-layer (rejects collisions with a validation error before DB write), complementing the existing DB-level constraint. No migration required; field-level flags (`required: true`, `index: true`, `unique: true`) match the current DB schema for all four collections.
- **UI:** No visual changes to admin forms outside the slug field row. The new affordances (lock/unlock + generate buttons) live inside Payload's SlugField component.
- **Dependencies:** None added. `payload@3.88.0`, `@payloadcms/next@3.88.0`, and `@payloadcms/ui@3.88.0` already export `slugField` / `SlugField` / `slugifyHandler`.
- **Skills:** Payload skill at `.agents/skills/payload/SKILL.md` is referenced in `AGENTS.md` but currently absent from the repo (`.agents/skills/payload/` does not exist). Payload work will proceed against the verified installed packages and the official ecommerce template at `~/.src/payload/templates/ecommerce/src/collections/` as a reference.
- **Tests:** No new tests in this change; the collection smoke tests (`tests/int/api.int.spec.ts`) exercise read access, not slug generation. A future change can add Vitest cases for collision-rejection and fallback behavior.
- **Design tokens:** No `DESIGN.md` impact — the admin panel chrome is owned by Payload; no public-storefront UI is touched.
- **Out of scope:** Localizing slugs, customizing the `slugify` function (the project uses Payload's default), versioning / drafts interplay, custom endpoints.
